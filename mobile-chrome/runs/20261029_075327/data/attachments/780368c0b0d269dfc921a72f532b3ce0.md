  17 |  *
  18 |  * Why the action is passed as a callback (not called before this helper):
  19 |  * Ordering matters. waitForResponse must be armed BEFORE the action fires, otherwise
  20 |  * a fast response can arrive before the listener is attached and the wait hangs until
  21 |  * timeout. Taking the action as a callback lets the helper guarantee the correct order
  22 |  * internally — the caller can't accidentally get it wrong.
  23 |  *
  24 |  * On coupling to route names (deliberate tradeoff):

  26 |  * same brittleness noted in routes.ts. It's kept because some assertions genuinely need
  27 |  * to wait for a mutation to complete on the server before checking persisted state
  28 |  * (e.g. reload + verify DB value). For purely visual outcomes, prefer asserting on the
  29 |  * user-visible result (error text, redirect) with web-first assertions instead of this.
